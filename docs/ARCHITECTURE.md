# AegisForge architecture

AegisForge v0.5.0 is a local-first static security workbench, Python source mapper, conservative source-to-sink analyzer, and deterministic mission runner. It has no external model API, telemetry endpoint, or cloud runtime requirement.

## Data flow

1. The CLI validates a local directory or starts the loopback-only web server.
2. The scanner traverses supported files while skipping symlinks, dependency/build directories, and files outside bounded resource limits.
3. Text analyzers inspect configuration and common source patterns; Python source is parsed with the standard-library AST module. Static rules cover unsafe YAML deserialization as well as common command, TLS, SQL, and payment-signature mistakes.
4. The Python project mapper creates a structural index of modules, imports, class/function definitions, enclosing scopes, and syntactic call sites. It does not resolve dynamic dispatch or claim a complete semantic call graph.
5. The Python data-flow visitor tracks common Flask, ASGI and Django request sources, `input()`, and `sys.argv` through local assignments and supported async iteration. It records source-line provenance and flags candidate flows into the first code/command/query argument of dynamic evaluation, shell-enabled subprocess commands, and SQL execution. It isolates class/function/lambda state, and does not confuse a lambda's deferred return value with an immediately evaluated value. It is intra-function and conservative; it does not establish exploitability or track all language/framework constructs.
6. Malformed Python creates an explicit incomplete-analysis warning. A scan that cannot parse one of its Python files is not represented as a clean AST analysis.
7. Findings are represented as immutable data objects with stable rule IDs, severity, location, redacted evidence, remediation, and confidence.
8. Report renderers produce text, Markdown, JSON, or SARIF.
9. Local baselines fingerprint findings and classify them as new, known, or resolved.
10. Repair proposals are generated without writes. Applying requires an explicit CLI flag, preserves backups, checks that files have not changed since preview, validates that the proposal exactly matches a built-in deterministic transformation, rescans, and rolls back when a targeted finding remains or a source-validation error occurs.
11. The browser workbench accepts a ZIP only from a same-origin loopback request. It validates archive member names, types, compression ratio, count and size limits; extracts only supported source/configuration files to a temporary directory; scans them without executing them; and deletes that directory after the response is built. The response includes security findings plus a Python structural map (module/import/class/function/call-site metadata). Paths remain relative to the uploaded archive, and the random temporary extraction directory name is replaced by a neutral label.
12. The mission runner uses an explicit registry of built-in local tools, including read-only project mapping. Each tool declares whether it mutates project data. The runner maps the project, scans it, prepares supported repair proposals, pauses in an approval-required state by default, and only calls the mutating repair tool when the user supplies the explicit approval flag. A fresh scan verifies the outcome. Mission results classify findings not covered by deterministic repairs as manual-review work; failed or incomplete missions expose every remaining finding for human review.

## Authority kernel

The authority kernel is a decision layer, not an executor or a universal controller. A trusted host supplies authenticated caller identity, a fixed capability catalogue, and a policy containing grants. The kernel itself does not authenticate callers or approvers, and policy-file integrity is the host's responsibility. Each grant matches exactly one subject, capability, and resource identifier, and must have a timezone-aware expiry. There are no wildcard grants or implicit inheritance. Unknown capabilities and unmatched or expired grants are denied.

Capabilities marked mutating require a short-lived, exact-scope, single-use approval token in addition to an active grant. The token is held in process memory, expires within 15 minutes, and is issued only after the host has authenticated the approver and received explicit consent. Expired tokens are pruned during subsequent issuance or authorization checks, and outstanding token storage is capped at 4,096 entries per kernel. The `issue_approval` method is not an authentication mechanism and must never be exposed directly to an unauthenticated client. Authorization returns a decision; it does not invoke a tool, command, service, or device.

The local tool registry provides a separate `call_authorized` invocation path. It checks that a registered tool has a capability mapping and that the tool's mutating flag matches the capability catalogue before asking the kernel for a decision; the handler runs only after an allow decision. This is an invocation path for trusted, explicitly registered local handlers, not dynamic tool discovery. The legacy mission CLI retains its explicit `--apply-supported-repairs` workflow for compatibility; callers that need policy-based authorization should use the authorized registry path.

Every tool used through `call_authorized` must also provide a resource-scope resolver. The resolver derives the exact resource from the same arguments passed to the handler; a separate caller-supplied resource string is not accepted. The built-in project tools derive `project:{canonical target path}` from their first target argument. The repair tool additionally rejects a caller-supplied backup directory outside the authorized project scope, because backup creation is a write side effect. The mission runner can receive an AuthorityKernel, a host-authenticated subject identifier, and an optional one-time approval token; it routes project mapping, scanning, repair preview, repair application, and post-repair verification through the authorized registry path. Without a repair capability grant the mutation is denied. With a repair grant but no token, the mission returns to a pending-approval state without changing files.

When an audit path is configured, every approval issuance and authorization decision is written to an append-only JSONL file using a sequential SHA-256 hash chain. Without a path, entries remain in process memory; production hosts should configure persistent logging. The chain is checked when the log loads and before each append; detected corruption, truncation after initialization, or write failure blocks the authorization call. This is tamper-evident operational logging, not a cryptographic signature or protection against a privileged attacker who can rewrite the entire log. One process should own each audit log.

The initial capability catalogue names project, service, and device operations. These names define policy vocabulary only; no production service or device connector is included. The explicit adapter layer is separate from the legacy tool registry: trusted application code registers a fixed adapter specification and exact operation-handler set. Every operation declares one capability, a read-only/mutating classification, an input validator, and a resource resolver. Validators and resource resolvers run before authorization and must be pure and side-effect-free; only the handler may perform an operation after an allow decision. Registration rejects unknown capabilities and classification mismatches; invocation validates input, derives the resource from the same argument mapping passed to the handler, and asks the Authority Kernel immediately before execution. The registry has no dynamic discovery, imports, shell access, or network behavior. Its catalog exposes metadata only.

The first adapter is deliberately a deterministic in-memory simulator. It can inspect a simulated service, increment a simulated restart counter, and change a simulated mode; it never touches the host operating system, a real service, a network, or a physical device. The two mutation operations use separate `service.restart` and `device.control` capabilities and each requires an active exact-scope grant plus a one-time approval token. Invocation accepts only plain JSON objects, copies and freezes nested objects/arrays, rejects non-finite numbers and custom Python objects, and enforces depth, node-count, string-length, and payload-size limits. Registration snapshots operation handlers and prevents public mutation of the declared operation map. These constraints reduce mutable-input and time-of-check/time-of-use risks, but adapters and their resolvers/handlers remain trusted application code. This validates the adapter boundary without implying that a live connector exists. Real integrations must be separately reviewed, narrowly scoped, and tested against their own threat model before registration.

## Trust boundaries

- The directory or ZIP being scanned is untrusted input.
- The scanner, project mapper, and data-flow analyzer never import or execute content from the scanned project.
- Data-flow findings are candidates based on a deliberately limited source/sink list; the analyzer does not prove exploitability or sanitizer correctness.
- ZIP entries are not allowed to create symlinks, special files, absolute paths, traversal paths, duplicate paths, or out-of-root writes.
- Reads and extraction are bounded by per-file, aggregate size, file-count, directory-count and archive-entry limits.
- The browser server binds only to a loopback IP literal and accepts only local Host and same-origin request headers.
- The browser response uses relative file locations and a neutral project label; it does not expose the temporary extraction directory name or absolute host filesystem paths.
- The browser UI renders finding content through text nodes; scan output is not interpreted as HTML. It also renders project-map fields through text nodes.
- Container rules identify privileged mode, hostPath mounts and privilege-escalation settings.
- The local tool registry does not perform dynamic discovery or import plugins. Its catalog exposes tool names, descriptions, and mutation flags but not callable handlers.
- Mutating tool calls require explicit approval at the registry boundary.
- Adapter invocations accept bounded JSON-only values; nested inputs are copied and frozen before scope resolution and handler invocation.
- Adapter registrations are explicit allowlists with per-operation capabilities and immutable metadata/handler mappings; no runtime plugin discovery or arbitrary command execution is provided.
- Evidence snippets are redacted before they enter reports.
- Rules are conservative and may produce false positives or miss issues; human review is required.

## Extension points

New analyzers should return Finding objects and use stable rule IDs in the shared catalog. New adapters must follow [docs/ADAPTERS.md](ADAPTERS.md): explicit allowlist registration, bounded immutable JSON input, per-operation capability mapping, and exact resource derivation. The simulator is not a production connector. A rule needs positive and negative tests before it is added. New repair rules must remain preview-first, verify exact source state before writing, preserve an original copy, run a post-check, and restore on verification failure. New mission tools must be explicitly registered, declare their mutation behavior, and have an approval-gate test when they can change data. New project-map visitors must remain bounded, AST-only, and side-effect-free. Data-flow extensions must add explicit positive and negative test cases for each new source, propagation rule, and sink. Browser result features must keep user-provided report data as text and must not expose temporary archive paths.

## Honest capability boundary

The mission runner is a deterministic workflow and permission-gated tool-execution foundation. The project map is a syntactic structure index, not a general semantic reasoner. The data-flow analyzer is a limited static approximation, not a complete taint engine. AegisForge is not a trained general-purpose AI model, does not autonomously invent objectives, and cannot control arbitrary software or devices. Those would require separate engineering, model research, and carefully scoped device adapters.
